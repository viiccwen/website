今年很幸運入選了 **[Google Summer of Code 2026](https://summerofcode.withgoogle.com/)**，成為 [Apache Software Foundation](https://www.apache.org/) 底下 **[Apache Mahout](https://github.com/apache/mahout)** 專案的 GSoC Mentee。

我申請的組織是 Apache Software Foundation，參與的專案則是 Apache Mahout。Apache Mahout 過去以分散式機器學習聞名，而近年也逐漸往分散式量子運算、數值計算與相關基礎建設發展。關於 Apache Mahout 的介紹，可以參考我另一篇文章：[Apache Mahout 簡介：從分散式機器學習走向分散式量子運算](https://vicwen.com/zh-tw/blog/zh-tw/zbout-apache-mahout)。

這篇文章主要想分享我準備 GSoC 2026 的過程，以及我自己在這段經歷中對開源社群、Proposal 撰寫和長期貢獻的一些理解。

## 為什麼是 Apache Mahout？

<img src="https://upload.wikimedia.org/wikipedia/commons/1/10/Apache_Mahout_Logo.png" width="50%" style="margin: 0 auto;" />

我開始投入 GSoC 2026 的時間其實滿早的，大約是今年一月左右。當時 Apache Mahout 社群的核心成員，同時也是現任 PMC 的 [Jay](https://www.linkedin.com/in/jiekaichang/) 問我是否有興趣加入 Apache Mahout。

一開始吸引我的原因，是 Apache Mahout 這個專案本身滿特別的。它同時結合了機器學習、分散式系統與量子運算相關方向，對我來說是一個很新奇、也很有挑戰性的專案。

相比單純做模型應用，我其實更希望參與一些偏底層、偏基礎建設，而且能被長期維護的開源專案。Apache Mahout 剛好符合這個方向。它不是那種短期看起來很熱門的專案，而是更接近一個需要長期理解、累積和投入的開源系統。

Jay 當時也提到，如果能夠持續深耕 Apache Mahout，未來不只是參與 GSoC，也有機會逐步成為 Apache Committer，甚至是 Apache PMC。這對我來說是一個很大的吸引力，因為我一直都很希望自己不是只完成一次性任務，而是真的能夠參與一個長期運作的開源社群。

因此相較於大多數人可能是在三、四月準備申請時，才開始尋找合適的組織、研究 issue、提交短期貢獻，希望獲得 Mentor 的青睞，我走的是一條比較不同的路。

我不是先把 GSoC 當成目標，再去找專案；而是先進入社群、熟悉專案、累積貢獻，最後 GSoC 變成這段投入過程中的其中一個階段。

## 開源社群內最重要的是 Trust

對我來說，GSoC 並不是一個只靠 Proposal 寫得好就能成功的申請。當然，Proposal 很重要，但在開源社群裡，更重要的是長期累積下來的信任，也就是所謂的 trust 或 credit。

開源專案和一般課堂作業、比賽或個人專案很不一樣。你提交的程式碼不是只有自己使用，而是會進入一個多人共同維護的 codebase。你的設計、測試、文件和溝通方式，都會影響整個專案未來的維護成本。

因此，對 Mentor 和組織來說，他們在評估一位 GSoC 申請者時，看的不只是「這個人技術強不強」，也會看這個人是否真的理解專案、是否能穩定溝通、是否願意接受 review、是否能把事情做完整，以及是否值得被交付一個重要的 Proposal。

我認為這也是開源社群中很核心的一點：信任不是靠一次大型貢獻建立起來的，而是透過許多次穩定、可靠、可被 review 的貢獻慢慢累積。

剛開始參與 Apache Mahout 時，我也不是一上來就挑很大的 feature 做，而是先從比較小的地方開始熟悉專案，包含閱讀既有程式碼、理解測試流程、觀察社群討論、修正一些小問題，以及協助 review 其他人的 PR。

這些貢獻表面上可能沒有那麼華麗，但其實很重要。因為它們能讓你逐步理解專案的 coding style、CI 流程、測試習慣、review 標準，以及社群成員之間如何協作。

截至 4/1 Proposal Deadline，我已經累積了超過 **25+ PRs** 和 **40+ reviewed PRs**。這對一個 GSoC 申請者來說，算是相當活躍的貢獻紀錄。

這些 PR 和 review 不只是為了讓履歷或申請資料看起來好看，而是真的讓我更理解 Apache Mahout 這個專案，也讓社群成員逐漸知道我是一個可以穩定參與、願意溝通、能夠持續投入的人。

我覺得這也是我後來能夠順利申請上的關鍵之一（Jay 說的）。

## Proposal 不是憑空寫出來的

在 GSoC 申請過程中，Proposal 當然仍然是非常重要的一環。

但我認為一份好的 Proposal 不應該是憑空想出來的，也不應該只是堆疊一堆看起來很厲害的技術名詞。它應該要建立在你對專案現況、社群需求、Mentor 期待和實作可行性的理解之上。

在撰寫 Proposal 的階段，我很常和 Mentor 確認架構與細節，確保這份計畫真的能夠在 GSoC 的時程內被完成，也確保它符合 Apache Mahout 長期發展的方向。

我自己在寫 Proposal 時，會特別注意幾件事情。

### 第一，目標要明確

不能只是寫「我要改善某個系統」或「我要加入某個功能」，而是要清楚定義這個專案最後會產出什麼，解決什麼問題，以及怎麼被驗收。

### 第二，時程要合理

GSoC 的時間有限，因此 Proposal 裡的 milestone 不能只是理想化的切分，而是要真的考慮開發、測試、review、修改和文件補齊所需的時間。

### 第三，要有風險意識

實作過程中一定會遇到不確定性，所以 Proposal 裡最好能夠說明可能遇到的風險，以及如果原本設計不可行時，有沒有替代方案。

### 第四，溝通方式也很重要

我不會只問 Mentor「這樣可以嗎？」而是會先整理自己的理解，提出幾個可能的做法，再請 Mentor 幫忙確認哪個方向比較符合專案需求。這樣的溝通比較像是在共同設計，而不是單方面等待答案。

對我來說，Proposal 撰寫的重點不是包裝自己，而是證明自己真的理解這個專案，也有能力把這件事從設計、實作、測試到文件完整地完成。

## 長期貢獻比短期衝刺更重要

很多人可能會把 GSoC 想成一個暑期計畫，覺得只要在申請季前找到 issue、做幾個 PR、寫一份 Proposal，就有機會入選。

這樣當然不是不可能，但我自己會更推薦**把 GSoC 當成長期開源貢獻的一部分**，而不是一次性的申請活動。

如果你很早就開始參與專案，你會有更多時間理解 codebase，也會更清楚哪些問題是真的重要、哪些設計是社群可以接受的、哪些地方需要和 Mentor 對齊。這些東西很難在短短幾週內完全補起來。

> 更重要的是，長期貢獻能讓社群看到你的穩定性。

開源社群其實不缺一次性貢獻者，但很缺願意長期維護、持續回應 review、願意改善品質的人。當你能夠穩定出現在社群裡，認真回覆討論、修正 PR、協助 review，Mentor 對你的信任自然會慢慢增加。

這種信任，在申請 GSoC 時會變成很大的優勢。

因為 Mentor 不只是看到一份 Proposal，而是已經看過你實際做事的方式。

## 入選之後的心情

後來也很幸運地，我從眾多候選人中脫穎而出，成為 **Google Summer of Code 2026 Mentee** 之一。

更有趣的是，後來得知 2026 年台灣入選 GSoC 的學生居然只有兩位。聽到這件事時其實滿驚訝的，也覺得這個機會比自己原本想像中更難得。

當然，入選 GSoC 不是終點，而比較像是一個新的開始。

對我來說，這段經歷最重要的地方，不只是拿到 GSoC Mentee 的 title，而是我真的進入了一個國際開源社群，參與實際的開源協作，也更理解 Apache Software Foundation 這類大型開源組織是如何運作的。

未來我也希望能夠持續深耕 Apache Mahout，不只是完成 GSoC 的 Proposal，也希望能在專案裡累積更多實際貢獻，朝 Apache Committer，甚至 Apache PMC 的方向努力。

## 給未來想申請 GSoC 的人

如果你未來也想申請 GSoC，我會建議不要等到申請季才開始。

越早進入社群越好。你不一定一開始就要做很大的功能，可以先從文件、測試、小 bug、範例、CI 或 review 開始。這些看似簡單的貢獻，其實都是理解專案和建立信任的好方法。

再來，不要只把重點放在寫 Proposal。Proposal 很重要，但它應該是你長期理解專案後自然產出的結果，而不是申請前臨時包裝出來的文件。

和 Mentor 溝通時，也盡量不要只丟問題，而是帶著自己的理解和方案去討論。這會讓對方知道你不是只想得到答案，而是真的有在思考專案的設計與取捨。

最後，我覺得 GSoC 最有價值的地方，不只是它能幫你履歷加上一行經歷，而是它能讓你真正進入一個國際開源社群，學習如何和世界各地的工程師一起協作，如何讓自己的程式碼被長期維護，以及如何在一個真實的大型專案中累積影響力，甚至能在這之中與其他人建立關係，獲得更多更廣的 Career Ladder 機會。
