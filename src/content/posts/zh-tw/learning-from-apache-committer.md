幾天前，我收到了一封來自 Apache Mahout PMC (Project Management Committee) 的信件（[後續的 Public Mail](https://lists.apache.org/thread/x92ozrhxb61t9g3tgqh3bb4zc328troc)）。

信件內容不長，大意是 Apache Mahout 社群經過討論與投票後，正式邀請我成為 Apache Mahout Committer。

收到信的當下，我當然非常高興。

從今年一月開始接觸 Apache Mahout，到參與 Google Summer of Code、閱讀專案程式碼、研究相關技術、提交 Pull Request，再到社群的眾人反覆討論實作方向、Bi-weekly Sync，這封信似乎替過去幾個月的投入，留下了一個具體的里程碑。

緊接著，我開始處理一連串 Committer Onboarding 流程：回覆邀請、確認 CLA (Contributor License Agreement)、等待 Apache Account 建立、設定 Apache ID、綁定 GitHub 帳號、設定 `@apache.org` 郵件，以及了解 Apache 內部使用的各種服務...。

看著自己的 Apache ID `vicwen` 正式啟用，成功進入 ASF GitHub Organization，確實有一種「終於走進來了」的感覺。

![](/asf-github.jpg)

不過，在最初的興奮過後，我也開始思考：

> 成為 Apache Committer，究竟代表什麼？

* 是可以直接將程式碼合併進專案？
* 是一個可以放進履歷、LinkedIn 和個人網站的頭銜？
* 還是代表自己的技術能力，正式獲得了國際開源社群的認可？

這些說法都不能算錯，但也都只說中了一部分。

真正參與 Apache 專案後，我才逐漸理解，開源並不只是找到一個 Issue、寫完程式碼、送出 Pull Request，接著等待 Maintainer 按下 Merge。

那些沒有直接出現在 GitHub Contribution Graph 上的事情——溝通、Review、測試、文件、授權、共識與信任——往往才是決定一個開源專案能否長期運作的關鍵。

這篇文章不打算介紹一套「如何快速成為 Apache Committer」的方法，因為 Committer 並不是完成多少 Issue、送出多少 Pull Request，就一定能取得的成就。

我更想記錄的是，從一名 Contributor 走到 Committer 的過程中，我遇到了哪些開源的眉眉角角，以及這段經歷如何改變了我對軟體工程、社群協作與開源貢獻的理解。

## Apache Committer 到底是什麼？

在談自己的心得前，可能要先說明 Apache Committer 到底是什麼。

對多數第一次接觸開源的人來說，最熟悉的角色通常是 Contributor，也就是透過提交 Issue、Pull Request、文件或其他形式，對專案做出貢獻的人。

大部分 Contributor 並沒有專案 Repository 的直接寫入權限。

當 Contributor 提交一個 Pull Request 後，通常需要等待 Maintainer 或 Committer 進行 Review，確認設計、程式碼品質與測試沒有問題後，才能將修改合併進專案。

Committer 則擁有專案 Repository 的寫入權限。

除了能夠提交自己的修改，也能 Review 並合併其他 Contributor 的貢獻。實際採用「Review Then Commit」還是「Commit Then Review」，則會依各個 Apache 專案的開發流程而有所不同。

但 Committer 並不是 Apache 裡的一種工程師職等，也不是累積足夠多 Contribution 後，自動升級得到的 Badge。

通常是既有的 Project Management Committee 成員觀察到某位 Contributor 長期而穩定地參與專案，認為他對專案具有足夠的理解，也願意承擔更多責任後，由 PMC 內部提名、討論並進行投票，再正式發出邀請。

Apache 官方對這件事有一段很值得注意的說明：

成為 Committer 與其說是一種獎勵或表揚，不如說是專案基於自身利益所做的決定。社群之所以邀請一個人成為 Committer，是因為相信這個人的加入，能夠幫助專案繼續發展。

換句話說：

> Committer 不是社群頒發給個人的成就獎章，而是建立在長期貢獻與社群信任上的責任。

一開始看到這段話時，我其實覺得有些冷酷。

畢竟大家投入大量時間參與開源，最後得到認可，多少會期待這是一種對個人努力的肯定。

但後來想想，這反而非常合理。

對一個需要長期維護的開源專案來說，最重要的問題從來不是「這個人已經完成了多少貢獻」，而是：

> 當我們把更多權限交給他時，他是否能讓專案變得更好？

## 不是 PR 越多，就越接近 Committer

剛開始參與開源時，我很自然地會關注一些可以被量化的數字。送出了多少個 Pull Request？有多少個 PR 被合併？GitHub Contribution Graph 上有多少格綠色方塊？自己是否出現在 Contributor List 的前幾名？

這些數字不是完全沒有意義。對剛開始投入一個專案的人來說，它們確實能帶來成就感，也能幫助自己確認是否持續投入。但參與一段時間後，我逐漸發現，PR 數量和對專案的實際影響，未必存在直接關係。有些修改可能只需要改動幾行程式碼，卻解決了許多使用者長期遇到的問題；有些 Pull Request 修改了數百行程式碼，最後卻因為缺乏測試、設計過度複雜，或沒有符合專案方向，而難以被合併。

對開源專案來說，一個好的貢獻不只是「程式可以執行」，還需要回答更多問題：

* 這個問題是否真的值得解決？
* 這項修改是否符合專案長期方向？
* 是否會破壞既有使用者的相容性？
* 測試是否涵蓋重要的邊界條件？
* 未來的維護者能否理解這段程式碼？
* 是否引入不必要的複雜度或相依套件？
* 其他開發者是否能在這個設計上繼續擴充？

這些問題通常不會反映在 PR 的數量裡。

Apache 官方也特別強調，程式碼並不是唯一被認可的貢獻形式。設計、文件、使用者支援、活動推廣、Review Pull Request，以及協助解決長期未處理的 Issue，都可能是維持專案健康的重要工作。

這也改變了我對「有效貢獻」的理解，以前我可能會認為，開源貢獻就是不斷認領 Issue、完成修改，再送出更多 PR；但現在，我會先觀察專案真正缺少的是什麼，有時候是一段沒有人看得懂的安裝文件，有時候是一個失敗很久的 CI Pipeline，有時候是缺乏測試的核心功能，有時候則是很多人提出相同問題，卻始終沒有人將答案整理進文件。

如果一個問題已經被五個使用者問過，那麼與其回答第**六**次，可能更好的做法是直接改善文件，讓第**七**個使用者不需要再問。

所以，我逐漸形成了一個對開源貢獻的新理解：

> 開源不是在自己的履歷上累積綠色方塊，而是在別人的專案裡減少未來的麻煩。

## Pull Request 是溝通工具，不只是程式碼容器

許多人第一次提交 Pull Request 時，最在意的通常是程式碼。

但在大型開源專案裡，Pull Request 不只是裝著程式碼的容器，它同時也是一個設計討論、知識累積與決策紀錄的場所。

當一個 Reviewer 打開 Pull Request 時，他不一定知道你過去研究過什麼、排除了哪些方案，也不知道你為什麼選擇目前的實作。

如果 PR Description 只有一句：**Fix the issue.**

那麼 Reviewer 就必須重新從頭理解問題。因此，一個完整的 Pull Request 通常需要清楚回答：

* 這個 PR 要解決什麼問題？
* 問題是如何發生的？
* 為什麼選擇這個實作方式？
* 是否考慮過其他方案？
* 有哪些可能的相容性影響？
* 如何測試這項修改？
* Reviewer 應該特別注意什麼？

這些文字不只是為了讓 PR 看起來比較正式，而是在降低 Reviewer 理解修改的成本，我也曾經遇過和 Mentor 討論後，原本的實作方向需要重新調整的情況。

第一個版本可能能夠執行，也成功通過部分測試，但當我們把問題放回完整的系統架構中，才發現還需要考慮更多輸入型別、邊界條件與既有行為。

這時候最困難的往往不是修改程式碼，而是接受自己原先對問題的理解並不完整。

Reviewer 可能會告訴你目前的設計不適合、測試不足、抽象層次不合理，甚至要求你重新研究整個實作方向。剛開始難免會覺得：「可是我已經花了很多時間」、「這個版本明明可以執行」、「真的需要考慮這麼多情況嗎？」

但後來我逐漸理解，Reviewer 評論的是目前呈現出來的設計，而不是否定貢獻者本身。對方可能維護這個專案多年，知道某些看起來奇怪的實作，其實是為了解決過去發生過的相容性問題；也可能知道一個看似乾淨的重構，會對下游使用者造成意想不到的影響。這些 Context 很難只靠閱讀當前幾個檔案就完全掌握。

所以，Pull Request 的反覆修改並不一定代表第一次實作失敗。它更像是透過公開協作，逐步縮小 Contributor 與 Maintainer 對問題理解的差距。

> 在開源專案裡，程式碼只是在回答「做了什麼」；真正決定一個修改能否被接受的，通常是你能不能說清楚「為什麼要這樣做」。

## 英文不是最大的門檻，資訊不完整才是

參與國際開源社群前，我曾經認為英文可能是最大的門檻。不光只是 GitHub 上的文字來往，還有 Bi-weekly Sync 開會，來自全球各地的人一同討論專案方向，擔心自己的文法不夠好、用詞不夠專業，或是在討論中無法快速理解其他人的意思。真正加入後，我才發現，多數開源社群並不要求每個人的英文都像母語人士。

說個有趣的，我們有次開 Sync，根本聽不清對面的印度人口音英文，只好請他再說一遍，甚至還說網路不太好，請他複述一次 XD。

畢竟大家來自不同國家，本來就有不同的語言背景。一段文法完美、卻沒有提供任何技術資訊的文字，幫助通常很有限。相反地，即使句型很簡單，只要把環境、操作步驟、預期結果與實際結果交代清楚，其他人就有機會理解並協助解決。

我也慢慢習慣在送出訊息前，先問自己：

> 如果我是完全不知道背景的 Maintainer，只看到這封信或這則留言，能否理解發生了什麼？

這個習慣不只對開源有幫助。在公司、研究團隊或任何多人協作的專案中，清楚傳遞 Context 都是一項非常重要的工程能力。

很多軟體開發上的問題，表面上看起來像是技術問題，實際上卻是資訊沒有被完整傳遞。

## 重要的事情，要留在公開討論裡

Apache 專案很重視公開且可追溯的溝通。有些專案會使用 Slack、Discord 或其他即時通訊工具，但正式的技術討論與決策，通常仍然需要回到公開 Mailing List、Issue 或 Pull Request 中。

一開始可能會覺得 Mailing List 是一種比較古老的協作方式。相較於即時通訊軟體，它的介面沒有那麼直覺，討論速度也不一定比較快。

但當我逐漸理解 Apache 的運作方式後，才發現公開溝通不是形式主義，而是開源治理很重要的一部分。

如果一個重要的設計決策只存在某兩個人的私訊裡，其他 Contributor 就無法知道：

* 當初為什麼做出這個選擇？
* 曾經考慮過哪些替代方案？
* 哪些限制導致目前的設計？
* 未來在什麼條件下可以重新討論？

更現實的是，那兩個人有一天可能離開專案，如果沒有公開紀錄，相關知識就會一起消失。因此，即使已經和 Mentor 或其他 Committer 私下討論過，重要的結論仍然應該整理到公開管道中。這不是為了重複工作，而是讓沒有參與當下討論的人，未來仍能理解決策脈絡。

Apache 官方的新 Committer 指南也特別提到，許多團隊都存在只保留在成員腦中或私人筆記裡的「部落知識」。將這些知識轉移到公開文件，能降低專案對特定個人的依賴。

## Community Over Code 不是一句口號

Apache 社群經常提到一句話：**Community Over Code.**

Community Over Code 的意義並不是程式碼不重要，而是再好的程式碼，如果沒有健康的社群，也很難長期存在，畢竟程式碼可以被重寫，架構可以被重構，框架和工具也會不斷被替換。

但如果一個專案沒有足夠的人願意 Review、回答問題、製作 Release、處理安全性問題與協助新 Contributor，那麼即使程式碼本身再優秀，專案也可能逐漸失去活力。

所以我判斷一個開源專案是否成功，通常會先看：

* Repository 最近是否有 Commit（活躍度很重要！）
* GitHub Star 數量
* Contributor 數量

若你想加入貢獻行列，通常要更注意以下問題：

* Pull Request 是否有人 Review？
* Issue 是否長期沒有人回覆？
* 專案是否願意培養下一批 Contributor？

這些事情可能沒有那麼顯眼，卻更直接地決定了一個專案的生命週期，Community Over Code 的核心，不是降低程式碼品質，而是建立一個有能力持續產生、Review、維護與改善程式碼的社群

**畢竟一份程式碼可能只能解決現在的問題，一個健康的社群，則能夠持續解決未來還沒有出現的問題。**

## 成為 Committer，不代表從此不需要 Review

成為 Committer 後，最明顯的改變之一，就是擁有更多專案權限。但擁有直接寫入 Repository 的權限，不代表從此每一項修改都可以自行決定。

相反地，權限越大，越需要謹慎。

Contributor 時，我最擔心的可能是：**我的程式碼能不能被合併？**
成為 Committer 後，需要思考的問題則逐漸變成：**我合併的程式碼，會不會為其他人帶來問題？**

一個修改可能會影響下游使用者、破壞向後相容性，或讓未來的維護成本增加。即使自己有權限直接修改，也不代表這樣做就是最好的選擇，較大型的功能、架構調整與可能影響使用者的變更，仍然應該經過公開討論與 Review。

Apache 的新 Committer 指南也提醒，取得直接修改權限後，更需要理解專案採用的協作模式，並對程式碼保持謹慎；即使是 Committer 的修改，仍然可以由其他 Committer 進行 Review。

但在開源社群裡，權限其實更接近責任：「我有權限這樣做」，不等於「我應該這樣做」。

真正重要的不是能不能直接 Merge，而是能不能判斷什麼時候可以行動、什麼時候應該尋求 Review，以及什麼時候需要先建立社群共識。

## Review 別人的程式碼，比想像中更困難

作為 Contributor 時，主要任務通常是完成自己的修改。但成為 Committer 後，除了繼續開發，也開始需要更主動地閱讀與 Review 其他人的 Pull Request。

Review 並不是簡單確認 CI 有沒有通過，一個完整的 Review 需要理解：

* Contributor 想解決的問題
* 修改涉及的程式模組
* 目前專案既有的設計
* 測試是否真的驗證了正確行為
* 是否存在沒有被考慮到的邊界條件
* 修改是否容易維護
* 是否符合專案的 Coding Style
* 是否涉及 License、依賴套件或安全性問題

雖說現在有 AI Assisted，但理解別人的 Pull Request 所花的時間，可能不比自己重新實作少，而且 Review 也需要考慮溝通方式。畢竟指出問題很容易，但如何讓對方知道問題在哪裡、為什麼需要修改，以及可能有哪些解法，則需要更多耐心。

更好的 Review 應該盡可能說明：

* 哪個情境下可能發生問題
* 目前設計違反了什麼假設
* 是否有既有實作可以參考
* 這是必須修改的問題，還是單純的建議
* 是否有其他可能的設計方向

同時，也需要避免要求 Contributor 把所有事情都做到完美，如果一個 PR 已經解決了原始問題，額外的重構或改善可以放到後續 Issue，就不一定需要無限擴張當前 PR 的範圍。好的 Review 並不是找出最多問題，而是協助貢獻者與專案，用合理的成本得到更好的結果。

**這也是我仍然需要持續學習的地方。🫡**

## 那些看起來不像寫程式的事情

收到 Committer 邀請後，我才發現，原來成為 Committer 還有不少技術與行政設定。

例如：

* 確認並提交 ICLA
* 選擇 Apache ID
* 設定 Apache Account
* 綁定 GitHub 與 Apache 身分
* 啟用雙因素驗證
* 設定 `@apache.org` 郵件
* 加入專案的 Mailing List
* 了解 Gitbox 與 Apache Infrastructure
* 設定 SSH 或 PGP Key
* 理解 Committer 與 PMC 的權限差異
* 熟悉 Release Vote 與相關流程

其中，ICLA 是 Individual Contributor License Agreement。

它不是將自己作品的著作權轉讓給 Apache Software Foundation，而是授予 ASF 足夠的權利，讓相關貢獻能夠依照 Apache License 發布。貢獻者仍然保有自己作品的著作權。

這些流程一開始可能會讓人覺得有些繁瑣。

但當專案的使用者遍布世界各地，甚至被大量企業整合進產品時，程式碼來源、授權、帳號安全與 Release 完整性就不能只依靠口頭保證。

一些看起來很官僚的程序，實際上是在保護 Contributor、專案、基金會，以及使用這些軟體的人。

除此之外，Committer 也不只是負責開發新功能。

其他工作還包括：

* 維護文件與網站
* 回答使用者問題
* Review Contributor 的 Pull Request
* 協助處理長期未解決的 Issue
* 關注 CI/CD 與建置問題
* 驗證 Release Candidate
* 參與 Mailing List 上的技術討論
* 留意程式碼與第三方依賴的授權
* 協助新的 Contributor 理解專案
* 將散落的知識整理成公開文件

這些事情單獨看起來都很瑣碎，也不一定能成為履歷上最顯眼的一行，但它們共同構成了一個大型開源專案能夠長期運作的基礎，它們大概就是我所理解的「開源眉眉角角」。

## 從完成任務，到開始對專案負責

回顧自己剛加入 Apache Community 時，我對貢獻的理解比較接近完成一個個明確的任務，找到 Issue、理解需求、修改程式碼、補上測試，再送出 Pull Request。

這種模式很接近一般的軟體開發流程，也比較容易衡量進度。但隨著參與程度增加，我開始意識到，專案裡有很多事情沒有明確負責人，也不一定會被整理成一個等待認領的 Issue。

有時候需要自己發現：

* 某段文件已經和目前版本不一致
* 某個測試缺少重要的邊界條件
* 某項設計需要先進行公開討論
* 某個舊 PR 其實只差最後一點協助
* 某些使用方式只有少數核心成員知道
* 新 Contributor 很難找到合適的切入點

Contributor 常常是在回答：**我可以完成什麼任務？**
而專案 Owner 更常問的是：**目前什麼事情對專案最重要？**

兩個問題看起來很相似，實際上卻代表不同的思考方式。前者主要關注自己可以產出什麼，後者則需要從整個專案與使用者的角度，判斷資源應該投入在哪裡。

Apache 官方也將這種態度稱為 **Project Ownership**，也就是優先考慮專案和使用者的整體利益，而不只是個人、公司或當前任務的需求。

我不認為自己已經完全做到這一點，但成為 Committer，至少讓我開始從不同角度看待每一項修改。不只是問：「這段程式能不能跑？」還會開始問：「這是不是專案真正需要的？」、「其他人能不能理解和維護？」、「這項決策有沒有留下足夠的紀錄？」、「它會不會增加未來的技術債？」

## 信任不是來自一次厲害的貢獻

成為 Committer 後，我另一個很深的感受是：

> 開源社群中的信任，通常不是來自某一次特別厲害的貢獻，而是來自長時間穩定而可預期的行為。

一次大型功能或許可以讓很多人注意到你，但社群在決定是否交付更多權限時，也會觀察更多事情：

* 是否會持續回覆 Review？
* 遇到不同意見時，能否理性討論？
* 修改出現問題後，是否願意負責處理？
* 是否尊重專案既有流程？
* 是否願意處理文件、測試等不顯眼的工作？
* 是否只在意自己的需求，還是會考慮其他使用者？
* 是否能和不同背景的 Contributor 合作？

這些事情很難透過單一指標衡量，畢竟它們需要時間，也需要多次互動才能被看見。

因此，Apache 官方也明確提醒，成為 Committer 沒有一套保證成功的條件清單。即使完成了許多建議事項，也不代表一定會被邀請；如果只是為了取得身分而刻意「刷條件」，反而可能傷害社群對貢獻者的信任。

這認為這和找實習、求職準備很不一樣。求職時，我們常常會研究評分標準，思考要補足哪些技能、累積哪些經歷，但開源社群不是一場按照固定 Rubric 評分的面試，更像是一段長期合作。

社群不是在判斷你是否完成了一張 Checklist，而是在判斷未來是否願意繼續和你一起維護這個專案。

## 成為 Committer 後，我真正得到的是什麼？

最直接的收穫，當然是 Apache Mahout Committer 的身分。

我擁有了 Apache ID、`@apache.org` 郵件與相關專案權限，也能更深入參與專案的開發與維護。

這些經歷對履歷與職涯當然有幫助。

尤其對一名還在學習與累積經驗的學生而言，能夠參與 Apache Software Foundation 旗下的專案，和不同國家、不同背景的開發者合作，是相當難得的機會。

但如果只把這件事理解為履歷上多了一個頭銜，我認為會錯過更重要的部分。這段經歷帶給我的真正收穫，是開始理解大型開源專案如何依靠一群沒有傳統上下級關係的人，透過公開討論、共識、信任與責任分工，持續維護多年。

我也學會：

* 接受自己的設計在公開 Review 中被挑戰
* 在資訊不完整時主動提出問題
* 將技術決策和討論脈絡留下紀錄
* 考慮程式碼之外的授權與維護問題
* 站在未來維護者的角度撰寫程式
* 理解「被信任」往往比「被看見」更困難
* 不只完成自己的任務，也開始關心整個專案是否健康

剛開始參與時，可能會想著：這個 Contribution 可以寫進履歷、這個 PR 合併後，可以證明我的技術能力，這些想法並沒有錯，我自己也確實因為開源遇見很多貴人、獲得了許多機會，很感謝這些人。🥹🙏

但參與得越深入，就越會發現，真正讓人留下來的往往不是履歷上的一行文字，而是對專案逐漸產生的責任感。你開始知道某個模組為什麼被這樣設計，知道某個 Issue 已經困擾使用者很久，也知道哪些功能需要有人繼續推動。

到了這個階段，貢獻就不再只是為了證明自己，而是因為你真的希望這個專案變得更好。

## 給想投入開源的人：不要一開始就追求 Committer

如果要給剛開始參與開源的人一個建議，我會說：**不要一開始就把「成為 Committer」當成唯一目標。**

因為當你太專注於取得身分，很容易開始用錯誤的方式衡量貢獻。你可能會不斷尋找最容易完成的 Issue，只在意 PR 數量，或是為了提高能見度而參與每一場討論。

但真正有價值的貢獻，並不一定是最容易被量化的那些。

比起詢問：

> 我要提交幾個 PR 才能成為 Committer？

更值得問的是：

> 我能做什麼，讓這個專案變得更好？

選擇一個自己真的願意使用、研究或長期關注的專案。先閱讀專案文件、Contributor Guide、近期 Issue、Pull Request 與 Mailing List，而不是看到第一個 `good first issue` 就立刻修改。從範圍清楚的小問題開始，熟悉測試、開發環境和 Review 流程，但不要永遠只挑最簡單的修改，回覆 Reviewer 的意見，即使暫時無法完成，也讓其他人知道目前的狀態。

除了寫新功能，也可以改善測試、文件與使用者體驗。

**最重要的是，保持穩定。**

短時間大量提交後完全消失，未必比長期、可靠且有品質的參與更有價值。開源社群最需要的，通常不是突然出現的英雄，而是遇到問題時，大家知道可以放心合作的人。

## 結語

成為 Apache Committer，當然是一件值得高興的事情。

但它比較不像遊戲裡完成任務後解鎖的新稱號，而更像是社群將一把專案的鑰匙交到你的手中，這把鑰匙代表你可以做更多事情，也代表別人相信你知道什麼時候應該使用它，什麼時候應該先停下來討論。

回頭看這段經歷，我最大的改變，或許是不再只用「我寫了多少程式碼」衡量自己的開源貢獻。我開始在意一個修改是否容易被理解、測試是否足夠、討論是否留下紀錄、新人能不能順利加入，以及即使某位核心開發者離開，專案是否仍能繼續前進。

程式碼當然重要，但程式碼終究會被修改、重構，甚至被整個取代。

真正讓一個開源專案持續存在的，是一群願意溝通、願意承擔責任，也願意將機會交給下一個人的社群。

這或許就是我成為 Apache Committer 後，才真正理解的 **Community Over Code**。

而對我來說，成為 Committer 並不是這段開源旅程的終點，它更像是社群告訴我：

> 我們看見了你的投入，也願意相信你能和我們一起，讓這個專案繼續走下去。

接下來，要做的事情才正要開始。✨
